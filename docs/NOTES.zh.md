# River Raid（Atari 8 位）— 发现

[English](NOTES.md) | [Русский](NOTES.ru.md) | [Українська](NOTES.uk.md) | [Deutsch](NOTES.de.md) | [Polski](NOTES.pl.md) | [Italiano](NOTES.it.md) | [Español](NOTES.es.md) | 中文 | [日本語](NOTES.ja.md)

映像：8192 字节，无 CART 文件头，加载到 $A000–$BFFF。代码约 5.9 KB（2941 条指令），数据约 2.3 KB。

## 入口点
| 地址 | 内容 | 如何找到 |
|---|---|---|
| $A000 | 启动 + 每帧主循环 | 卡带尾部（$BFFA） |
| $B2A5 | VBI（VVBLKI $0222）：POKEY 声音、帧计数器、每帧寄存器 | A0D1 处写入 $0222/$0223 |
| $B500 | DLI（VDSLST $0200）：逐行复用精灵 | A0C7 处写入 $0200/$0201 |
| $B485 | 空的 IRQ | 写入 $0216/$0217 |

## 帧
- `L_AE99`：等待 VCOUNT < $50（新的一帧开始），准备显示列表和精灵。
- `L_A197`：等待 VCOUNT >= $50，读取摇杆（PORTA、TRIG0/1），执行游戏逻辑。
- `A18D`：等待 VCOUNT = $78，然后写 NMIEN（$C0 = DLI+VBI，$40 = 仅 VBI）。
- 循环走一圈 = 一步逻辑，所以“每帧调用一次 update()”的模型是正确的。

## 移植要注意的事
1. **随机数。** `RANDOM`（$D20A，POKEY 的多项式）在 3 处被读取。游戏逻辑只在 A205：每 16 帧选一个敌人槽位（0–10），在其标志中置位 $40。另外两处读取（B362、B3D0）只给声音提供噪声。读到的值取决于读取时的 CPU 周期（POKEY 的 17 位多项式以机器时钟运行）。移植版模拟这个计数器（`port/src/pokey_random.h`），并像真机开机一样从时钟启动它；做逐帧对比时，原版的值取自基准跟踪（`random.log`）。
2. **PAL/NTSC。** PAL 位从 $D014 读取（A06A），保存在 $BF，用来选择显示列表的变体（$B77A，复制到 $3FA9 处的显示列表）、补给站上限 `$CB`（$2E/$2F），以及 B135/B14F/B741 处的分支。没有任何东西补偿帧率：在 PAL 上游戏以每秒 50 帧运行，大约慢 17%。从来没有单独的 PAL 版本：英国磁带版就是同一份代码（见“英国磁带版”）。移植版的 `-pal` 设置补给站上限；PAL 显示列表和 50 Hz 还没有重现。
3. **来自系统的字体。** 代码把字符集从系统 ROM（$E000/$E100/$E300）复制到 $0600–$09FF。这是外部依赖：需要自带字体或使用用户的 ROM（Altirra OS 是自由的）。
4. **与电子束绑定。** 精灵由每行使用 WSYNC 的 DLI 核心绘制；在 C++ 中它变成按帧状态工作的软件渲染器。
5. **声音。** 驱动程序完全在 VBI 中（$B2A5–$B484）：4 个 POKEY 声道，AUDF/AUDC 由 $C6、$7A–$7F、$50、$24 以及表 $B4AC/$B4C0/$B4E1 计算得出。重现这个驱动程序再加一个 POKEY 核心，就足以精确一致。
6. **代码风格。** 整块式，变量被不同子系统重复使用，标志打包在位中。完整的映射需要来自模拟器的跟踪。

## 数据表（按代码中的引用）
全部通过 `port/src/rom.h` 中有名字的函数读取。
- $B4AC（4）：按摇杆上/下决定的引擎音色（AUDC）；$B4C0（17）：坦克炮弹呼啸声的音高；$B4E1：奖励生命的声音。
- $B4D1：坦克的形状（指针对，在 AEB9 通过 $A1/$A2 读取）。
- $B776（4 字节）复制到 $3F00（显示列表开头）；$B77A（15 字节，PAL 上用后 15 字节）复制到 $3FA9，即显示列表的其余部分。
- $BB70（60 字节）：面板文字，复制到 $1000；$BEEE（64）：Activision 字样 → $06C0；$BF2E（112）：面板符号 → $0818；$BF9E（24）：“P1”/“P2” → $08D0；$BFB6（48）：“1982, 1983”的数字 → $07D0。
- $BAAF：下一种坦克；$BAC5：炮弹颜色；$BB24：下一种物体（动画）；$BB40：从 $B900 起的物体形状偏移。

## 基准运行（已完成）
`oracle/rr_oracle` 在 libatari800 上运行原版，记录每一帧的 RAM、每次 POKEY 写入和每次 RANDOM 读取（见 `oracle/README.zh.md`）。
- 游戏用 START 键开始；在标题画面按开火不会开始。
- atari800 从时钟启动 POKEY 生成器；加 `-seed` 时各次运行逐字节相同。
- RANDOM 读取：扫描线约 249 是 VBI 中的声音，扫描线 190–192 和 241 是游戏逻辑（A205）。对 C++ 来说，这意味着在校验模式下游戏的随机值取自 `random.log`，而不是模拟出来。

## 关卡生成器（已由跟踪确认）
- 河道和物体的放置由 `sub_B183` 中的 24 位软件 LFSR 驱动，作用于 $AA/$AC/$AB。由 A756 和 A767 调用。
- 一步：`fb = bit7(AB) ^ bit2(AB)`，然后链条左移 AA←fb、AC←bit7(AA)、AB←bit7(AC)。Python 模型解释了跟踪中 268 次变化中的 265 次；其余 3 次是重新载入。
- AA/AB/AC 的初始值是 $E3/$D4/$F7。它保存在 $66–$68，在开始后和坠毁后（从桥重新开始）于 A3C8 恢复。
- 用不同的 POKEY 种子跑 1000 帧，$AA–$AC、$66–$68、物体类型（$0500…）和它们的 X（$0516…）完全相同。只有槽位标志 $42–$4C（来自 A205 的 $40 位）、工作字节 $07 和栈不同。
- 结论：关卡总是同一个。`RANDOM` 只影响敌人的行为（谁得到 $40 标志）。游戏开始时敌人的移动似乎是关闭的（A297 处对 $60 的检查），所以在短运行中看不出来。

## 地形生成（代码 A6FD–A9D7，绘制 AA8C–AB4B）
河岸不是以图像保存的，而是每行几个数字。屏幕的每一新行是生成器的一步，之后这一行被画进屏幕的环形缓冲区（行地址来自显示列表，$3F04/$3F05）。

**卷动（来自代码）。** 每帧速度 `$59` 两次加到累加器 `$30`，每次溢出产生一新行。速度 128 时正好每帧 1 行；`$59 ≥ $FE` 时不累加直接产生一行。

**结构（来自代码）。**
- `$2F` — 块内行号，0…31。
- `$5A` — 段内剩余块数（2）。
- `$5D` — 到桥为止剩余的段数，重新载入为 16；到头时调用 `sub_B194`。
- LFSR `sub_B183` 在每一行走一步，`$23` 第 7 位置位的行除外（通往桥的直道）。
- 在段的边界，新的目标宽度 `$5F` 取自 `$AA` 的低半字节并加以限制（最小 2，最大 15/14/8，视 `$2D`、`$60`、`$B5` 而定），然后 `$34 = $5F·4`。

**每行的数字。**
| 地址 | 内容 | 状态 |
|---|---|---|
| $52 | 河岸位置 | 已校验（随机游走，见下） |
| $C3 | 游走方向：+1、$FF（−1）或 0 | 已校验 |
| $54 | 岛 / 内部部分的半宽 | 已校验（平滑） |
| $53 | 水面宽度；按 `$54` 步长的 −2 倍变化，因此总宽度保持不变 | 已校验 |
| $34、$35 | `$54` 的目标和朝它前进的步长（差 < 32 时 ±1，否则 ±2） | 已校验 |
| $2D | 第 7 位 — 岛模式（改变绘制），第 6 位 | 来自代码 |
| $C4、$C5 | `$52` 的边界：`$60 < 3` 时 $1C…$24，否则更宽（1…$40，按 `$60`、`$052D`、`$36` 有不同变体） | 来自代码，跟踪中见到 28…36 |
| $23 第 7 位 | 桥附近河岸按表 `$BA8F[$2F] + $52` 走，没有随机 | 通过 C++ 校验（`terrain_check`） |
| $052D | ≠ 0：河岸被拉进 $18…$28 的走廊 | 通过 C++ 校验（`terrain_check`） |

**河岸的随机游走（A84F–A96A），已校验。** 每行取低半字节 `n = $AC & 15`（本行这一步之后的 LFSR 字节）：
- 若 `$C3 = 0`，开始移动：`n ≥ 8` 时 +1，否则 −1；
- 若河岸已经在移动：`n < 8` 时不动；`n = $D` 时掉头并走一步；`n = $F` 时，若 `$0E`（岛上为 `$0D`）小于 `$5F` 或 `$2C` 则不动；其他任何值都走一步；
- 会越过边界 `$C4/$C5`、或撞上当前槽位 `$4E` 中物体（类型 ≥ 8；边界用 `$54/$34`、`$0516+X`、`$B5`、`$0521+X` 计算）的一步，改为原地掉头。

时序上的细节：槽位和 `$4E` 取帧开始时的值，而 `$54/$34/$2D/$B5/$37` 取本帧已重新计算的值。按这条规则，模型在全部 4669 行上与跟踪一致。

**岛的平滑（A7FB–A824），已校验。** 只要 `$35 ≠ 0`，每行执行 `$54 += $35` 和 `$53 −= 2·$35`。`$54` 到达 `$34` 时，步长 `$35` 清零。在 4825 行上校验，其中 1195 行确实发生了变化。

**装饰（房屋、山）。** 在块开头（`$2F = 0`）且 `$AC` 第 5 位置位时开始。偏移、宽度和行数按 `$AA` 和 `$5F` 取自表 `$BBCC`、`$BBD4`、`$BBB2`、`$BBEB`，位图指针取自 `$BBF0`。通过 C++ 校验。

**物体。** 每 16 行在最高的空闲槽位（`$4D`−1）放一个新物体；类型按 `$AB` 通过表 `$BB1C` 选出，精灵宽度取自 `$BBA2`（写入 `$0521+X`，即 `SIZEP3`：船为 1，桥为 3，其他为 0），行数取自 `$BB60`（+4）。物体还在画入期间（`$32` 行），河岸绕开这个物体（`$4E`）。通过 C++ 校验。

**桥。** 生成器只在桥的位置画一条直的河道（河岸来自表 `$BA8F`），并在 `$42+X` 中带 `$80/$84` 标志（`$23` 的副本）的槽位放一个类型 `$0E` 的物体。桥本身只在显示时、在 DLI 中（B575–B5FC）出现：对标志第 7 位置位的槽位，每行的河岸颜色 `COLPF0` 取自表 `$B4E5`（`04 04 04 04 08×6 1C 1C 06×5 04 04 04`：灰色的路面条纹和黄色的标线），所以道路盖在河岸像素上横贯整个屏幕；水面上的桥身是该槽位四倍宽的 P3 精灵，与船和直升机相同。物体之后，河岸颜色从 `$0B` 恢复（`$D2`/`$D6`：河岸按段的奇偶交替两种绿色）。路上的坦克是精灵 P1（`$39`）。桥的位图行生成后不再改变（在 119 行上校验）。

**每行的颜色和精灵（通过 C++ 校验，`port/src/river_draw.cpp`）。** 基础颜色来自垂直消隐（B408–B43E）：水 `COLPF2` = $84（闪光时 $42），岸边 `COLPF1` = $20，河岸 `COLPF0` 来自 `sub_AFD0`：`($23 & 4) ^ $D6`，当最新的物体（`$4E`）是 y < $5C 的桥时第 2 位翻转。DLI 带着扫描线计数器从 `$4D` 向上遍历槽位（在新行进入的第 20 行值为 $5D）：第一个满足 `0 ≤ y + $BB60[类型] − 计数器 ≤ $BB60[类型]` 的槽位给出行 r；形状为 `$B900 + $BB40[种类（标志第 3 位置位时 +16）] + r`，颜色为 `$B700 + $BB30[类型] + r`，HPOSP3 = `$0516+X`（32 = 缓冲区左边缘），SIZEP3 = `$0521+X`；对桥的槽位 COLPF0 = `$B4E5 + r`。与原版第 20 行相比：用生成器位置时 96.8% 的行相同，用游戏物体位置时 98.1% 相同，其余所有行都出现在路上坦克活动期间。

**演示模式与屏幕底部（通过 C++ 校验，`port/src/status_bar.cpp`）。** 不按 START 时，游戏从开机起卷动第 1 局的河：滚动字幕从第 11 帧开始走，河从第 38 帧开始，每帧 1 行，穿过一座座桥，用的是同一个生成器（第 20 行的条带在 19 960 帧上与 C++ 一致，移动物体除外）。$3F00 处的显示列表：24 个空行，160 行模式 E，然后是面板：从 $1000 起 3 行模式 6（正常宽度，`CHBASE` $08，颜色 $1E/$8E/$1E/$00 在 $06 上，`PRIOR` 4），内容由 `$BB70` 填入；燃料指针是位于 `$5B/8 + $5C` 的导弹 1。最后一行：带 `HSCROL` 的宽模式 6，`CHBASE` $06，颜色 $0C，文字在 `$B800 + $3FB3`；只要 `$2A` ≠ 0，VBI（B44B）就让 `HSCROL` 7→0 步进，然后把文字前移一个字符（$4B…$D6，循环），并带着标志 `$27` 一起移动。标志是四倍宽的 player 3（数据 $FC）加上 player 2（$FF），后者每行向左偏移一个周期，颜色为 `$B48D`。$0600/$0800 处的字符集是系统字体（A0FB）加上卡带自己的字符，位于 $06C0、$0818、$08D0、$07D0（“1982, 1983”的数字）。

**物体移动、坦克、导弹（通过 C++ 校验，`port/src/game.cpp`、`display.cpp`）。** 每 16 帧，由 `RANDOM & 15` 选出的槽位（11–15 → 6–10）在 `$42+X` 中获得第 6 位（“醒来”），除非它是仍在画入的物体。种类 7（喷气机）每帧移动；种类 8–13 只在醒来后、从第 2 座桥起（`$60 >> 1 ≠ 0`）、按槽位奇偶隔帧移动（`X ^ $18 ^ $33`），种类 $0C 只在 `$18 & 2 = 0` 的帧移动；每步 1 个周期，第 3 位 = 向左，在 $2C…$D4 间回绕。当物体的精灵在屏幕上碰到岸边颜色（P3PF 第 1 位）时，DLI 置位 `$42+X` 的第 0 位；下一步就把方向反转一次（第 4 位标记掉头，直到接触结束）。$0C 以下的种类每 8 帧通过 `$BB24` 换一次动画帧（种类 7 及以上每 2 帧）。坦克（`$38`–`$3A`）每 16 帧前进一次（种类 4–7 为每 4 帧），直到 player 1 碰到岸边颜色，然后（`$41` 第 7 位）开炮：炮弹是 player 0，`$50` 从 0 数到 $38（飞行表 `$B4AF`，速度 `$3E/$3F`），然后是爆炸帧。槽位 `$51` 中种类 $0A/$0B 的直升机发射导弹 0（`$C1` x，`$C2` y，步长 `$C0` = ±2），直到它打中河岸（M0PF）。DLI 在每个物体之后读取并清除碰撞寄存器，因此碰撞是按槽位知道的（`$1A`–`$22` 保存槽位号）。在重放 RANDOM 的情况下，C++ 在从开机起 19 900 帧演示模式上与原版的 RAM 一致。

**声音驱动（通过 C++ 校验，`Game::soundDriver`）。** 在 VBI（B2A5–B3D8）中每帧一次，AUDCTL 保持 0（64 kHz 时钟，17 位噪声）。`$C6` ≠ 0：声道 1 上响起开始提示音（$40/$AF），其余关闭。声道 1：声音事件 `$7A` 1–4，持续 `$7B` 帧（音高 $39/$11/$1F/$3F，音量来自 `$7B`）；否则，飞机飞行时，`$5B` < $40 时为燃料警告（每 63 帧一声提示，低于 $04 时为下降的音调），或者是引擎：AUDF = $1F − `$59`/16（坠毁后为下降的 `$052C`），AUDC 来自摇杆上/下位（`$B4AC`：正常 $84，$83/$86）。声道 2：爆炸噪声 `$7C`（AUDF = RANDOM | $18），或在游戏中为直升机导弹 `$7F`。声道 3：射击 `$7D` 或计分声 `$7E`（`$B4E1`）。声道 4：坦克炮弹 `$50`（飞行中用 `$B4C0`，然后是噪声）。演示模式是无声的：`$76` ≠ 0 关闭声道 1，其他也都不会触发。

**有玩家时的游戏（通过 C++ 校验，`port/src/game.cpp`）。** `$76` 是飞机的状态：0 飞行；$FE…$80 爆炸（126 帧，`$5E` 飞机帧每 8 帧下降）；然后 $7F：如果还有生命，河被重置（`sub_B0F1`，X = $12，在只运行中断的 13 帧内清空屏幕和 player-missile 内存），并以 `$59` = $FE（每帧 2 行）重新填满，同时 `$76` 从 $7F 数到 $30；到 $30 时扣一条命，`$052C` = $80（上升的引擎声）；到 $2F 时飞机在桥边等待、不卷动，直到摇杆任何移动或开火把 `$76` 设为 0、`$59` 设为 $40。没有生命时：游戏结束（最高分 `sub_B261`，校验字节 `$90`–`$9F`，`sub_B21A`：`$76` = `$2A` = $FF，滚动字幕显示“Game over”）。飞行中（A3E9–A5B4）：飞机与物体碰撞（`$1D`）：种类 7–$0E 坠毁（桥还会计入 `$2E`），种类 $0F 加油（每帧 `$5B` + 2，声音 `$7A` 4/3）；炮弹爆炸（`$1E` 且 `$50` ≥ $11）、直升机导弹（`$21`）或河岸（`$1B`）坠毁；燃料每帧烧掉 $20/256；横向移动会加速（`$2B` += 8，小数 `$58`），帧 7/8/9；速度 `$59` 在 $40 与 $FE 之间 ±2，摇杆居中时回到 $80；子弹（导弹 2，从 `$56` 起 8 行，每帧向上 6 行）摧毁种类 ≥ 7 的物体（`$1C`），按类型查分数表 `$BB0B`，每 10 000 分奖励一条命（最多 9）。被摧毁的桥计入 `$61/$62`，带走站在桥上的坦克，并从第 5 座桥起让附近的坦克开炮。`sub_B1C0` 决定下一架飞机从哪里出发：越过被摧毁的桥则从下一段开始，否则退回一个检查点。双人游戏（`$09` 为奇数）在每架飞机之后交换 `$60`–`$6A` 与 `$6B`–`$75`（`sub_B247`）；玩家 2 使用第二个摇杆（PORTA 的高半字节）。START（A673）开始新游戏（B0F1，X = $29，13 帧）；SELECT/OPTION 每 30 帧切换到下一局；键盘上任何键都会暂停（`$24`：3 → 2 暂停 → 1 → 0）。

**绘制（通过 C++ 校验）。** 一行是 48 字节位图（ANTIC 模式 E，每字节 4 像素），由填充段（子程序 `AFEC`/`AFF0`/`AFF4`：`$AA`、`$FF`、`$55`）和来自 `$B800` 处表的 2 字节岸边片段（`B034`/`B03B`）组成：河岸、水、岛（`$2D` 第 7 位置位时）、水、河岸。像素位置除以 4 是字节号，低 2 位选择岸边片段。装饰的一行由 `B01A` 复制。两岸不是镜像的：右边缘由左边缘通过水宽和岛宽算出，所以河道弯弯曲曲。在 C++ 的 2200 行上：两侧边缘都移动时，944 次中有 810 次移动方式相同；河道中心在 71 到 122 像素之间游移。

## C++ 生成器（`port/`）
- 全部逐行处理（A711–AE96 及子程序）都已移植到 `port/src/river_gen.cpp`。校验工具 `port/tools/terrain_check` 把生成器的每个字段和每个新屏幕行的 48 字节与原版比较。
- 结果：整条河 119 758 行没有差异；从零开始（`startGame`）也一致。
- 生成器既不依赖玩家（机器人对比不操作飞行），也不依赖 `RANDOM`（3 个种子，120 000 帧，逐字节相同，包括屏幕条带）。
- 屏幕：ANTIC 模式 E 位图，每行 48 字节（192 像素，每字节 4 个），环形缓冲区，新行地址在 `$3F04/$3F05`，每行 −$30。像素值：1 河岸，3 水，2 岸边，0 很少（在岸边片段内部）。
- 第 1–8 局：`$09` 选择表 `$B494`–`$B4A8` 的一行：LFSR、河岸和起始段。第 1–2 局从第 1 座桥开始，3–4 从第 5 座，5–6 从第 20 座，7–8 从第 50 座。这些是同一条河的检查点：C++ 到达第 5/20/50 座桥时的值与表中完全一致（`$B4A4`：关卡，`$B4A8`：BCD 的桥计数）。移植版通过运行生成器建立同样的表，用于 `-seed N`（从 LFSR 状态 N 开始的第 1 局的河；卡带的河是 $F7D4E3 = 16241891）和 `-bridge N`（每局都从第 N 座桥开始，1–9999；80 之后关卡为 79、80、79……）。
- `$CB` 在 NTSC 上为 $2E，在 PAL 上为 $2F（A077，来自 PAL 寄存器）；它影响块开头出现补给站的几率（AC48）。PAL 和 NTSC 上的河略有不同。
- 开始和重生：`sub_B0F1` 从 `$BAE1` 载入 $4D–$5F，清空 $2B–$4C 和 $0500–$05FF，把起始桥放进槽位 10（类型 $0E，y=$4A，高 $17），模式 $23 = $84/$80。然后 A3C8 从检查点 $66–$69 恢复 LFSR 和河岸。之后游戏以每帧 2 行（速度 $FE）生成 160–165 行来填满屏幕。
- 校验中的陷阱：在以每帧 2 行填满屏幕期间，模拟器的帧边界可能落在两行之间，所以这些帧的逐帧比较是错的。正常游戏中（每帧一行）快照总是落在行边界上。

## 关卡地图
- 河岸生成器不依赖飞机：绕开物体看的是类型 `$050B`，物体被击落时它不变。`$60`（段号）每 1024 行在桥被生成时增加，而不是在桥被摧毁时（机器人那局中 `$60` 在第 1133 帧变化，桥在第 1177 帧被摧毁）。
- 所以可以用无敌的飞机录下整个关卡：`rr_oracle -ghost` 修改模拟内存中的 5 个字节（A3E9/A424/A42E/A432 `LDX 标志` → `LDX #$FF`，A443 燃料消耗 $20 → 0）。120 000 帧中没有一次坠毁。
- 正常速度下关卡每帧正好移动 1 个屏幕行，新行出现在屏幕第 20 行。每帧第 20 行的条带与实时画面一致，移动物体除外。
- `$60` 增长到 $50（80），然后在 $4F/$50 间交替；段边界上的 LFSR 状态在 117 段内没有重复，所以河不会循环，但第 80 段之后难度不再增加。
- 按段生成图像：`tools/level_map.py`。查看器已作为页面“Карта реки River Raid”发布。

## 方法
规则先从反汇编清单中读出，再用基准跟踪检查（`tools/verify_trace.py`）。跟踪不一致时，就去找读错的地方。例子：加油是从代码 A3E9–A453 推出的（包括因进位标志而不是 +1 而是 +2 这一不明显之处），并由跟踪确认；唯一的不一致说明了碰撞检查发生在物体在槽位间移动之前。

## 英国磁带版
`River Raid.cas`（英国，600 波特）：两个文件。引导文件（7 个块，位于 $0A00，入口 $0A06）检查内存是否至少 24K（“NOT ENOUGH RAM MEMORY - NEED 24K”），显示标题画面，把 $2200 字节载入 $1000，然后跳到 $3000。这是搬到 RAM 中的卡带代码，逐条指令比较过：从 A21B 起全部 2900 多条指令都是相同的操作；代码和数据从 $A000 移到 $1000，游戏的 RAM 页上移 $2000（显示列表 $3F00 → $5F00，屏幕环 $2000–$3FFF → $4000–$5FFF，$1000 → $3F00），零页变量大多 +2（$25 → $A1，$28 → $A2）；表中的指针以同样方式偏移。真正的差异：
- 初始化（A000–A0EE）移到 $3000，并在 $E4/$E5 中计算所载入代码的校验和；
- 复制保护：如果校验和不对，或 HATABS 中有 `D:` 处理程序（从 DOS 启动），主循环会卡死或跳进一条指令的中间。卡带自己的保护（A151–A158）在 $6000 不是 $47 时把 $FF 写进自己位于 $A19B 的代码：在 ROM 中无害，在 RAM 副本中致命；
- 滚动字幕写着“1982, 1983, 1984”：多一个字符“4”（复制到 $07C0），文字长 5 个字符，卷动的开始/结束 $20/$4B → $1B/$46。

生成器、游戏逻辑、声音和数据表完全相同；PAL 检查也一样。

## 确定性与跳转
- **河只取决于它自己。**生成器既不依赖玩家，也不依赖 RANDOM，也不依赖物体：绕开物体时看的是它的类型（`$050B`）和仍在画入、因而还不会移动的那个物体的 X。LFSR 每行走一步，通往桥的直道除外：从一座桥到下一座桥正好 993 步。从第 1 局开始，它的周期是 16 766 977 步，而 gcd(993, 16 766 977) = 1，所以桥上的状态要过 16 766 977 座桥才会重复（加上关卡的奇偶 79/80，也许要再加倍；未实际跑过）：大约不停飞 9 年。面板上的桥计数器只有 4 位：9999 之后显示为空（0000），然后从 1 继续。
- **关卡。**在 sub $B194（`sectionCheckpoint`）中，关卡在加 1 之前若 ≥ $50 就当作 $4E，所以 80 之后关卡在 79/80 之间交替。奇数段和偶数段不同（奇数：宽度代码总是 7，物体可在横向任意位置；偶数：随机宽度、有岛），交替保留了两种段；难度不再增加。
- **检查点。**在每座桥上，生成器保存 LFSR 和河岸。从第 N 座桥开始（游戏中的 `-bridge N`、坠毁后重生）会恢复它们：此后的河与不停飞行时相同，物体则不同（全部刚刚摆好，没有谁醒来或移动过）。
- **RANDOM。**一个 17 位计数器，每个机器周期沿着一个由 131 071 个状态构成的固定循环走一步。移植版保存它在循环中的位置（`src/pokey_random.h`），所以任意周期的值都能立刻得到。因此哪个敌人醒来，取决于开机以来的帧数。
- **物体只在屏幕上时才存在。**物体由生成器放在顶部，从底边滚出后就消失，大约 200 帧之后；坦克（prepare：`tankY` ≥ $BC）和它的炮弹也一样。所以任一时刻的全部状态，由该时刻的河加上最近约 200 帧决定。`Game::skipFrame` 执行“只有河”的一帧：卷动、帧计数器、演示模式计时器、滚动字幕，以及 prepare() 对河状态所做的事（坦克和炮弹离开屏幕下方；没有这一步，旧坦克会让生成器放不下一辆）。然后是完整的帧。与从头飞到底比较过（4 条河以及 `-bridge` 起点，每种 77 个点，每个点之后 6000 帧）：从 200 个完整帧起，每一帧画得一样，全部状态也相同。不活动的坦克、炮弹或直升机导弹的变量可能留有不同的旧值；它们在使用前会重新设定，也不会被画出来。
- **演示模式中谁也不会摧毁谁。**坦克炮弹的爆炸只在飞机的飞行代码（A4C1）中摧毁物体，而没有飞机时这段代码不运行。
- **屏幕保护。**无输入 128 × 2048 帧（约 73 分钟）后，$78 的第 7 位置位：主循环停止（A1F5），屏幕变黑，直到任何摇杆、控制台键或键盘键。游戏保留这一行为；查看器每帧清零 $78。
- **查看器中的跳转**（`viewer/river_view.cpp`）。锚点（河的状态和计数器，约 170 字节）在当前进程中每 1024 帧一个；完整快照（约 16 KB）每 128 帧一个，只保留在当前时刻之前的最后 8192 帧，以及重放位置周围（64 个）。显示第 L 行时，从最近的快照或锚点出发：先只跑河，再跑 400 个完整帧（如果之后要往回滚动，再多 512 帧）。B 只用生成器找到下一座桥，再以同样方式飞过去；`-bridge N` 从河的起点飞过去。内存：每座桥约 190 字节，外加固定的约 2 MB。
- **游戏中的存档**（F7 / F8，手柄上 LB / RB；`Game::save` / `load`）。与查看器不同，这里无法让任何东西“自行归位”：飞机会与物体相互作用，所以保存整个状态，但只保存无法重新算出的部分。保存的有：变量（`GameState`）连同 player-missile 内存、生成器的状态，以及屏幕内存最旧一行之前的生成器状态和行数；屏幕内存（最近 256 行河道，12 KB）由此重新生成，因为这些行只取决于生成器（为此游戏在运行时记住屏幕上每一行之前的生成器状态，`keepLineStates`，约 31 KB）。不保存的有：按扫描线的数据（`scan`），display() 每帧都会清空并重建；以及画面，由下一帧画出（暂停时也一样：暂停只停止游戏逻辑）。player-missile 内存（1.25 KB：4 个“玩家”是宽 8 像素、高 256 行的竖条，再加上导弹；视频芯片每行为每个读一个字节）无法重新算出：游戏在别处画一个形状之前并不总是擦掉旧的，残留部分会参与碰撞；但它几乎全是零。所有内容都按零的连续段压缩（一个零字节，后跟该段的长度）：加上 RANDOM 计数器和 POKEY 声音共 400–620 字节（原先连同屏幕内存和画面要 110 KB）。已验证：12 个存档（不同速度飞行、爆炸、坠毁后重新填充屏幕、游戏结束、暂停），每个之后 900 帧：画面和声音都相同。
